# Research: Magic-link Sign-in (RM-3)

Decisions for the plan. Stack and conventions are fixed by `docs/tracklite-spec.md` section 12, RM-1 (`specs/001-project-foundation`), `AGENTS.md` and the constitution; Next.js APIs were checked against the bundled guides in `node_modules/next/dist/docs/` (Next 16.3.8). The owner questions Q1 to Q3 were answered on 2026-10-01; each answer is recorded where the question was raised (R3, R1, R9) and in plan.md "Resolved owner questions".

## R1. Database access (Drizzle ORM or postgres.js)

- **Decision (owner question Q2, answered 2026-10-01: keep postgres.js for RM-3, no `drizzle-orm`)**: queries are written with the already approved `postgres` (postgres.js) tagged templates through the existing `db()` client, in a few `src/server/*.ts` modules that take the `Sql` handle as their first argument (as `applyMigrations` does). Schema changes stay hand-written SQL in `migrations/`, applied by `npm run db:migrate` (AGENTS.md); `drizzle-kit` is not needed either way.
- **Rationale**: section 12 named Drizzle ORM, and RM-1 deferred asking for `drizzle-orm`/`drizzle-kit` to RM-3 (001 plan Q3); section 12 now names postgres.js (owner, 2026-10-01; plan.md follow-up resolved). They are not in `package.json`, so Constitution IV requires the owner's approval before use. RM-3 has five small tables and about a dozen queries; postgres.js covers them with no new package.
- **Alternatives considered**: `drizzle-orm` for RM-3's queries (declined by the owner for RM-3, Q2; section 12 now names postgres.js instead); `drizzle-kit` generated migrations (would replace the RM-1 migration runner, which AGENTS.md fixes); `pg` driver (another package, no gain).

## R2. Sending email: production provider (DEC-003)

- **Decision**: Resend, called directly over its HTTP API with the built-in `fetch` (`POST https://api.resend.com/emails`, `Authorization: Bearer <RESEND_API_KEY>`, JSON `{ from, to, subject, text }`), with a 10 s `AbortSignal.timeout`. Any non-2xx answer, network error or timeout is a failed send (STD-6, FR-009). No SDK package.
- **Rationale against DEC-003**: HTTP API (yes); bounce webhooks on every plan (yes, needed by RM-13 / API-003); sends from the team's own domain after adding its SPF and DKIM DNS records (yes); free plan of 3,000 emails a month and 100 a day costs $0, so NFR-009's $20 is left to hosting (checked on resend.com/pricing, 2026-10-01). Sign-in mail for a team under 15 is far below the daily cap. API key only in the server's `.env.local` (OPS-006).
- **Risk carried to RM-13**: notification email volume must stay under 100 a day on the free plan; the cheapest paid plan is $20 a month, which alone would break NFR-009. RM-13 re-checks this; it does not affect RM-3.
- **Alternatives considered**: Postmark (paid plan about $15 a month, leaving too little of NFR-009 for the VPS); Amazon SES (cheapest per email, but its API needs SigV4 request signing and bounce reports arrive through SNS with certificate checks, more code without an SDK); Mailgun and Brevo (comparable free tiers; no advantage over Resend for this team).
- **Owner action (not a question)**: create the Resend account, add the sending domain and its DNS records, and put `RESEND_API_KEY` and `EMAIL_FROM` in the server's config file. Needed before production sign-in (RM-2), not for local development.

## R3. Sending email: local development (Mailpit)

- **Decision (owner question Q1, answered 2026-10-01: option (b))**: no new package. `src/server/email.ts` has one function, `sendEmail({ to, subject, text })`, which picks the transport from the environment (R6). In local development it calls Mailpit's HTTP send API with the built-in `fetch`, the same way production calls Resend: `POST http://{MAILPIT_HOST}:{MAILPIT_PORT}/api/v1/send`, JSON `{ "From": { "Email": EMAIL_FROM, "Name": "Tracklite" }, "To": [{ "Email": to }], "Subject": subject, "Text": text }`, with the same 10 s `AbortSignal.timeout`; a non-2xx answer, network error (for example Mailpit not running) or timeout is a failed send, exactly as for Resend.
- **Settings**: `MAILPIT_HOST` and `MAILPIT_PORT` say where Mailpit's web UI and API listen (`localhost` and `8025` by default); the sender is `EMAIL_FROM`, as in production. Mailpit's SMTP port (1025) is not used. Mailpit started without auth options (`mailpit`) accepts the send API without credentials, so no credential setting is added.
- **Rationale**: Node has no built-in SMTP client, and the spec requires `MAILPIT_HOST` and `MAILPIT_PORT` in local development, with `EMAIL_FROM` as the sender in both environments (FR-029, FR-031). The HTTP send API needs no approval, shares the `fetch` code path and test stub (`vi.stubGlobal("fetch")`, R20) with production, and adds no protocol code. Mailpit stores and shows the message exactly as an SMTP delivery would; checked against the locally installed Mailpit v1.30.7 (`200` with the message ID, message listed with sender name "Tracklite").
- **Alternatives considered**: (a) `nodemailer` to Mailpit's SMTP port 1025 (a new package for local use only); (c) a hand-written SMTP client over `node:net`, about 50 lines (protocol code the project would own).

## R4. Tokens and hashing (SEC-003, FR-026)

- **Decision**: magic-link and session tokens are 32 bytes from `crypto.randomBytes` (256 bits), encoded base64url (43 characters). Only `sha256(token)` (hex) is stored, in a unique `token_hash` column; lookups hash the presented value and compare by equality in SQL.
- **Rationale**: tokens are high-entropy, so a fast unsalted hash is enough to make stored values useless as links or sessions (SEC-003.1) without slowing lookups; `node:crypto` is built in.
- **Alternatives considered**: bcrypt/scrypt (needed only for low-entropy secrets such as passwords; would also prevent indexed lookup); HMAC with a server secret (adds a secret setting for no extra protection here).

## R5. Session cookie (SEC-004, FR-017)

- **Decision**: cookie `session`, value = the raw session token, attributes `HttpOnly; SameSite=Lax; Path=/; Max-Age=34560000` (400 days, the browsers' cap), plus `Secure` outside local development. The server is the only authority on expiry: a session is valid while `ended_at` is null and `last_active_at` is within 30 days (FR-015). Three places answer `Set-Cookie: session=; Max-Age=0; …` to clear it: signing out (`DELETE /api/sessions/current`), a page request through the Proxy that carried an invalid cookie, and an API `401` for a request that carried a `session` cookie.
- **Rationale**: `HttpOnly` keeps it from page scripts. `SameSite=Lax` is exactly the clarified rule: sent on top-level link clicks from other sites (a magic link in Gmail), never on cross-site form posts or background requests. A long `Max-Age` with server-side sliding expiry avoids re-sending the cookie on every request while keeping REQ-006.1 (still signed in after 40 days of daily use).
- **Alternatives considered**: `SameSite=Strict` (would drop the cookie on the Gmail link click, contradicting the clarification); `__Host-` prefix (requires `Secure`, which breaks plain-HTTP local development in Safari); a 30-day `Max-Age` refreshed on each request (more `Set-Cookie` traffic for the same result).

## R6. "Local development" versus production

- **Decision**: local development is any `NODE_ENV` other than `production` (`next dev` and Vitest). `next build`/`next start` set `production`. In production: `Secure` cookies, Resend, and the app refuses to start without `RESEND_API_KEY`. Otherwise: no `Secure` flag, Mailpit, and the app refuses to start without `MAILPIT_HOST` and `MAILPIT_PORT`. `APP_URL` and `EMAIL_FROM` are required in both.
- **Rationale**: section 12 has exactly two environments, and Next already sets `NODE_ENV` for each; no extra setting or feature flag.
- **Note**: running `npm run build && npm start` on a laptop counts as production, so it needs the Resend settings. This matches "outside local development" (FR-029).

## R7. Start-up settings check (FR-029)

- **Decision**: `src/server/config.ts` keeps `readSettings()` (database only; still used by `db()` and `db:migrate`) and gains `readAppSettings()` returning `{ appUrl, emailFrom, email: { kind: "resend", apiKey } | { kind: "mailpit", host, port } }`, throwing `Missing setting: NAME` for the first missing one. It also checks the format of each setting it reads (FR-029) and throws `Invalid setting: NAME` for the first bad one:
  - `APP_URL`: parses with `new URL`, its protocol is `http:` or `https:`, and the value equals that URL's `origin` (an absolute origin with no path, query or fragment).
  - `MAILPIT_PORT` (local development only): digits only, an integer from 1 to 65535.
  - `EMAIL_FROM`: passes `isValidEmail` from `src/server/emailAddress.ts`, the one email rule (R16).
  `checkSettings()` in `src/instrumentation-node.ts` calls both, so `next dev`/`next start` exit 1 with the message (`Missing setting: NAME` or `Invalid setting: NAME`), as RM-1 already does for `DATABASE_URL`. The setup command, `npm run db:seed` and `npm run db:migrate` call only `readSettings()` (FR-029).
- **Rationale**: `db:migrate` must not need email settings, so database and app settings stay separate functions. `APP_URL` is required because the email link must be built from configuration, never from the request's `Host` header (a forged `Host` would put a valid token in a link to another site). Requiring a bare origin keeps `{APP_URL}/sign-in?token=…` and the return-to origin check (R8) well formed.

## R8. Protecting pages: Proxy with a database check (STD-1, FR-019, FR-020, FR-023)

- **Decision**: `src/proxy.ts` (Next 16's renamed middleware; runs in the Node.js runtime by default, `proxy.md`) runs on every page request (matcher excludes `/api` and `/api/…`, `/health`, `/_next/static`, `/_next/image` and `/favicon.ico`). It reads the `session` cookie and validates it against the database with `validateSession` from `src/server/session.ts`, the same function `requireMember` uses for the API (one indexed `UPDATE … RETURNING` that also records activity, R14). The Proxy only authenticates; it makes no role decision (R9). Then:
  - `/sign-in` with a `token` query parameter present at all (`searchParams.has("token")`, even empty or repeated): always passes (FR-023); the page uses the first value.
  - `/sign-in` without a token, or `/`: signed in → redirect `/my-issues`; signed out → `/sign-in` (for `/`) or pass.
  - Any other path: signed in → pass; signed out → redirect `/sign-in?next=<path and query>` (Next's internal `_rsc` parameter removed) and clear a stale cookie.
- **Rationale**: one gate covers every page, including unknown addresses (the Not found page now needs a session, FR-019) and expired sessions (REQ-006.2 must return to the requested page, which only the Proxy knows). Next's guide recommends cookie-only "optimistic" checks in Proxy for performance; for a team under 15 on one server, one indexed query per request is negligible, and it removes the need for every page to repeat the check. Server components still read the member for display through a request-cached `currentMember()`.
- **Alternatives considered**: cookie-presence check in Proxy plus a database check in each page (every later page must remember the call, and an expired session would lose the return-to address); a check in the `(app)` layout (layouts do not re-run on client-side navigation).
- **Return-to**: the `next` query parameter on `/sign-in`. The sign-in form sends it with the request; the server stores the validated value on the magic link (`destination`), so it travels with the link to any browser (REQ-005.4). Only same-app paths are kept: a string starting with a single `/` (not `//` or `/\`), at most 2,048 characters, whose `new URL(value, APP_URL)` has `APP_URL`'s origin; anything else becomes `/my-issues` (User Story 3 scenario 6). Any such path is accepted, with its query string kept (for example REQ-040's list filters), including `/api/…`, `/health`, `/sign-in` and `/sign-in?token=…` (spec clarification, FR-012, FR-020); no path inside the app is special-cased.

## R9. Protecting the API and the permission layer (STD-1, STD-2, SEC-006, FR-021)

- **Decision**: `src/server/permissions.ts` is FR-021's one permission layer, and the only place a role is checked. `src/proxy.ts` (pages) and `currentMember()` in `src/server/session.ts` (server components) only authenticate, through the same `validateSession` function in `src/server/session.ts` that `requireMember` calls; they decide who is signed in, never what the role may do. Later slices that need a page-level role check (for example a page that renders `NotAllowed`) call the rules in `permissions.ts` too, not their own. `requireMember(request)` returns the signed-in member (id, full name, username, role) or throws `ApiError(401, "Not signed in")` (an API-only message the UI never shows, like RM-1's "Not found"); `requireAdmin(member)` throws `ApiError(403, "You don't have permission to do that.")` for a Member (section 7's admin-only rows). Every protected route handler calls `requireMember` first; later slices add their section 7 rules beside `requireAdmin`. In RM-3 the protected `/api` handlers are the catch-all and every other method on the three sign-in paths, all one shared handler: `unmatchedRoute` in `src/server/permissions.ts` (wrapped in `apiRoute`: `requireMember(request)`, then `ApiError(404, "Not found")`), which answers `401` signed out and `404` signed in; AGENTS.md's catch-all sentence (a JSON `404`) is amended in the same change (plan.md outline step 10). Only the three exempt endpoints themselves (`POST /api/sign-in-links`, `POST /api/sessions`, `DELETE /api/sessions/current`) do not call `requireMember`.
- **Other methods on the sign-in paths** (FR-019, STD-1): a route file that exports only its own method would leave the others to Next, which answers an unexported method with a bare `405` outside `apiRoute` (no JSON body, no log line) and auto-implements `OPTIONS` as a `204` with an `Allow` header and `HEAD` from `GET` (`route.md`; `next/dist/server/route-modules/app-route/helpers/auto-implement-methods.js`). So `src/app/api/sign-in-links/route.ts`, `src/app/api/sessions/route.ts` and `src/app/api/sessions/current/route.ts` each also export every other method Next supports (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`, minus their own) as `unmatchedRoute`, so they answer exactly as the catch-all: `401` "Not signed in" signed out, JSON `404` signed in, one timing log line each. Alternative rejected: a separate handler per file (three copies of the catch-all's code).
- **Owner question Q3 (answered 2026-10-01: accepted)**: `requireAdmin` has no caller in RM-3 (the first admin-only action is RM-4), but FR-021 and User Story 6 require it now, with unit tests. Principle II's "kept before any code uses it" exception covers only `src/components/`, so it is recorded as plan.md's Complexity Tracking entry, which the owner approved; `requireAdmin` ships in RM-3 with its unit tests (User Story 6 scenarios 2 and 3). Deferring it to RM-4 was the rejected alternative.
- **Not allowed page state** (STD-2, User Story 6 scenario 4): a shared `NotAllowed` component in `src/components/ui/` with its own component test, covered by Principle II's shared-component exception. No RM-3 page renders it.
- **UI hiding** (FR-022): server components get the member's `role` from `currentMember()`; later slices hide their controls from it. No extra client context is added now (Principle II).

## R10. Rejecting cross-site writes (SEC-004, FR-018)

- **Decision**: `apiRoute` rejects every `POST`, `PUT`, `PATCH` and `DELETE` whose `Sec-Fetch-Site` header is present and not `same-origin`, or, when that header is absent, whose `Origin` header is present and differs from `APP_URL`'s origin (the app's, spec Assumptions), with `403` "You don't have permission to do that." before the handler runs. Requests with neither header (non-browser clients) pass; they carry no browser cookies by accident.
- **Rationale**: all NFR-006 browsers send `Sec-Fetch-Site` on every request; a check in the shared wrapper covers every current and future write in one place. Combined with `SameSite=Lax`, a cross-site form post has neither the cookie nor a passing header.
- **Alternatives considered**: CSRF tokens (more state and a hidden field on every form, for no gain with Fetch Metadata); checking only `Origin` (absent on some same-origin requests in older browsers).

## R11. Sign-in request limits and request IDs (SEC-001, FR-005, FR-008)

- **Decision**: two tables (data-model.md): `sign_in_attempts` (each request that passed the limit check: normalised email, IP address, time) and `sign_in_requests` (the `requestId` of each accepted request). Flow for `POST /api/sign-in-links`:
  1. Validate `requestId` (a UUID); missing or invalid → `422` "Invalid input" (counts toward nothing).
  2. `requestId` already in `sign_in_requests` → answer "Check your email" again, ignoring the `email` and `next` sent with it (even an invalid email gets this first answer, FR-005); nothing sent or counted.
  3. Validate `email` with `isValidEmail` (R16); invalid → `422` with the field error (counts toward nothing).
  4. In one transaction, take `pg_advisory_xact_lock` on the email key and then on the IP key (always that order), check both limits, and if allowed insert the attempt row; commit. Limited → `429` "Too many sign-in requests. Try again later.", nothing counted or sent.
  5. Active member for `lower(email)`? No → record the `requestId`, answer "Check your email". Yes → create the magic link, send the email; on failure delete that link row and answer `503` "We couldn't send the email. Try again." (not recorded, already counted); on success record the `requestId` and answer "Check your email". A send that times out (R2's 10 s) is a failed send even if the provider still delivers the email later: its link row is already deleted, so that email's Sign in button shows "This link has expired" with "Request a new link" (spec edge case, accepted; CHK033).
- **Limit rule** (FR-008, Clarifications): for a key (email or IP) with limit N (5 or 20), let `last` be its latest counted request. The key is blocked when `now() < last + 1 hour` and at least N counted requests fall in `(last - 1 hour, last]`. This is "at most N per hour", and a block lasts until one hour after the last allowed request, since refused requests are not counted.
- **Concurrency**: two simultaneous requests with the same `requestId` both arrive before either is recorded, so each is evaluated as new; this matches FR-005 (only an accepted, already recorded request is replayed). The disabled button (STD-5) keeps this from happening in normal use.
- **Client IP**: the rightmost entry in `X-Forwarded-For`, with whitespace at either end trimmed (spec Assumptions). When the header is missing or that trimmed entry is empty, the IP key is the fixed value `unknown`, so all such requests share one 20-per-hour bucket (spec Clarifications). Next's server fills that header with the socket address only when it is absent (`base-server.js`). In production RM-2's reverse proxy appends or overwrites it with the real client address, so the rightmost entry is the address the proxy saw. **Dependency on RM-2**: the roadmap's RM-2 scope now includes that reverse-proxy rule; until RM-2 ships there is no public deployment, and a client that sends its own `X-Forwarded-For` can choose the value and evade the per-IP limit, which the spec accepts.
- **Email normalisation**: trimmed and lowercased for the limit key and member lookup.

## R12. Using a link and starting a session (REQ-005, FR-011 to FR-014)

- **Decision**: `POST /api/sessions` with the JSON body `{ token, requestId }` (a body that is not JSON → `422` "Invalid input", like `POST /api/sign-in-links`), handled by `redeemSignInLink` in `src/server/signIn.ts`:
  1. Read the browser's current session (if any).
  2. Look up the link by `sha256(token)` (a malformed token simply matches nothing). If a member is signed in and the link is not theirs (other member's, unknown or malformed) → answer `signedInAsOther` with the signed-in member's full name; nothing used or changed (REQ-005.5, FR-011). This check runs before the replay check, so a replay is reached only when nobody is signed in or the signed-in member is the link's member, and never silently replaces another member's session (for example Sam's answer was lost, Alex then signed in on that browser, and Sam's tab retries: Alex is asked to sign out and keeps the session).
  3. Replay check (FR-012, CHK029): answered from an earlier session only when **both** a live session (valid by data-model.md's rule: `ended_at` null, `last_active_at` within 30 days, member active) has `request_id = requestId` **and** that session's `magic_link_id` is not null **and** `sha256(token)` equals the `token_hash` of that link. Then, when the browser's current session (the link's own member's, since step 2 passed) is a different session from the replayed one, end it first, as step 4 does on the normal path, so that browser is left with exactly one live session; then issue the replayed session a fresh token (the raw one is never stored), set the cookie, answer `signedIn` with the link's destination as the first time. A matching `requestId` alone is never enough, so the plainly stored `requestId` cannot be used as a credential; any other request goes on to step 4. A session that is ended, lapsed or belongs to a member deactivated since is not live, so a repeat for it is not a replay either; it goes on to step 4, which answers `expired` for the used link. `sessions.magic_link_id` is nullable with `ON DELETE SET NULL` (data-model.md), so RM-14's DATA-004 deletion of used or expired links leaves their sessions valid with a null link; a repeat for such a session matches no link in step 2 and goes on to step 4, which answers `expired` (like any unknown token), with no cookie from the old session.
  4. Otherwise, in one transaction: `UPDATE magic_links SET used_at = now() … WHERE token_hash = $1 AND used_at IS NULL AND expires_at > now() AND` the member is active `RETURNING …`. No row → `expired` (FR-013). Row → end the browser's current session if any (the link's own member, FR-012), insert the new session, write the log line "sign-in, member {username}", set the cookie, answer `signedIn` with the link's destination (or `/my-issues`).
- **Token value**: the body's `token` is the first value of the page's `token` query parameter (FR-023). An empty, malformed or missing token is never a `422`: it matches no link and is handled like an unknown one (`signedInAsOther` when another member is signed in, else `expired`). Only a body that is not JSON (parsed as `POST /api/sign-in-links` does) or a missing or non-UUID `requestId` is a `422`.
- **`requestId` per page load** (FR-012, CHK021/CHK022): the landing page makes one `crypto.randomUUID()` when it loads and sends it with every Sign in click from that load, including a retry after the "Couldn't save. Try again." toast. So a retry after the server used the link but its answer was lost passes step 3 and gets the first answer (signed in), unless a different member has signed in on that browser meanwhile (step 2). Another tab or a reload makes a new `requestId`, so Sign in there after the link was used gets `expired`, even though the browser is now signed in as the link's member (spec edge case). A request that repeats a recorded `requestId` with a different but valid, unused link fails step 4's insert on the unique `sessions.request_id`: the code catches that unique-key violation, the transaction rolls back (no session is created and that link stays unused) and it throws `ApiError` `422`, so nothing reaches the error log (FR-012's one exception to the normal path). The landing page never sends this, since one page load has one token.
- **Rationale**: the conditional update makes the link single-use under concurrent clicks (two tabs: the second gets `expired`, spec edge case). Answers are `200` outcomes, not error codes, because "expired" and "signed in as another member" are normal page states, and this lets the landing page use RM-1's `saveJson` unchanged (any non-2xx → the STD-9 toast).
- **Landing page on open** (`GET /sign-in?token=…`): server-rendered; never changes the link's state (REQ-005.3, mail scanners). Signed out → Sign in button for every token. Signed in → Sign in button only if the link exists and belongs to that member; otherwise the REQ-005.5 message. Expiry is never checked on open, so opening reveals nothing about the token.

## R13. Sign-out (REQ-006, FR-016, FR-019)

- **Decision**: `DELETE /api/sessions/current` (resource-style; the token stays in the cookie, never the path). Sets `ended_at` on whichever live session the browser's cookie names at that moment (in a stale landing-page tab this may be a different member's session than the page showed, for example Bob's after Alex signed out elsewhere and Bob signed in; the spec accepts this, CHK034), always clears the cookie, always answers `204`, never `401`. The cross-site check (R10) applies. The client then does a full navigation: to `/sign-in` from the app shell, or `window.location.reload()` on the landing page so the same `/sign-in?token=…` loads (FR-016's exception). A network or server error shows "Couldn't save. Try again."
- **Rationale**: ending only this browser's session row keeps other browsers signed in. Keeping ended rows (instead of deleting them) is what DATA-004 (RM-14) later cleans up.
- **Client call**: RM-1's `saveJson` only sends `POST`, so sign-out uses its own few-line `fetch` (Constitution I prefers a little duplication over widening the shared helper for one caller).

## R14. Activity and the 30-day rule (REQ-006, FR-015)

- **Decision**: validating a session is one statement, `validateSession` in `src/server/session.ts`: `UPDATE sessions SET last_active_at = now() FROM members … WHERE token_hash = $1 AND ended_at IS NULL AND last_active_at > now() - interval '30 days' AND members.active RETURNING` the member. Every authenticated page request (Proxy) and API request (`requireMember`) runs it. Server components reuse the result within one render through React's `cache()`.
- **Rationale**: one round trip both checks and records activity; the spec allows coarser refreshes but per-request writes are trivial at this scale and need no extra rule. All time comparisons use the database's `now()`, so tests age rows by updating their timestamps instead of faking clocks.

## R15. Sign-in log line (SEC-007, FR-027)

- **Decision**: move RM-1's private `writeLine` from `src/server/api.ts` to `src/server/log.ts` (exported `writeLogLine`), used by `apiRoute` and by the sign-in code, which writes `{ "time": …, "message": "sign-in, member sam" }`. A failed send logs `{ "time": …, "level": "error", "message": "magic-link email failed", "status": <provider HTTP status or "network"> }`, without address, token or link.
- **Rationale**: two callers now share it. The request log already drops query strings; Next's own request log is off (RM-1); no token, link or cookie value is ever passed to the logger. Tests capture `process.stdout.write` during a full sign-in and assert no token, link or cookie value appears (SC-005).

## R16. First-admin setup command (OPS-001, FR-001 to FR-003)

- **Decision**: `scripts/setup.ts`, run as `npm run setup -- --email owner@acme.com --name "Owner Name" --username owner` (arguments parsed with `node:util` `parseArgs`). `npm run db:migrate` must have run first (FR-001); on an unmigrated database the first query fails, and the command prints the database error and exits 1 with nothing created. It loads `.env.local` like `db:migrate`, validates with the shared profile rules in `src/server/members.ts` before touching the members table (so invalid input is refused with its field lines on any database, FR-003), then in one transaction takes `LOCK TABLE members IN SHARE ROW EXCLUSIVE MODE`, refuses with "Setup already done" if any member exists, else inserts an active Admin. Exit code 0 on success, 1 on any refusal, printing one line per invalid field (`full name: Name required` or `full name: Too long (max 60)`, `username: 2 to 20 lowercase letters, digits or hyphens`, `email: Enter a valid email address.`).
- **Rationale**: the table lock makes two simultaneous runs create at most one admin (spec edge case). The profile rules (trim, 1 to 60 characters, "Name required" when blank, "Too long (max 60)" when over 60 characters after trimming; username lowercased then `^[a-z0-9-]{2,20}$`; the shared email rule) are written once, in a `validateProfile` function private to `src/server/members.ts` and tested through `createFirstAdmin` (Constitution II: nothing is exported for tests only).
- **One email rule** (FR-003, FR-005, CHK001): `src/server/emailAddress.ts` exports `isValidEmail(value)`: trim whitespace at either end, then at most 254 characters and a match for the WHATWG HTML standard's "valid e-mail address" rule for `<input type="email">` (its published regular expression). It is the only email check: the setup command (through `members.ts`), `POST /api/sign-in-links` (the sign-in form's input, R11) and `EMAIL_FROM` at start-up (R7) all call it. The sign-in form itself does no client-side check (design.md: the server's `422` drives the field error).
- **Owner-facing text**: the command is not a screen (design.md); "Setup already done", "Name required" and "Too long (max 60)" are the spec's strings, the other two lines reuse the field rules' wording.

## R17. Initials (REQ-003.4, FR-025)

- **Decision**: `src/lib/initials.ts`: trim, split on whitespace, take the first grapheme (built-in `Intl.Segmenter`) of the first and of the last word, `toUpperCase()` each; one word gives one character. Unit-tested with every REQ-003.4 example.
- **Rationale**: graphemes keep a multi-code-point first character (accented letter, emoji) whole; built in, no package.

## R18. Page structure after sign-in arrives

- **Decision**: the root layout keeps `html`, `body`, `AriaRouterProvider` and `ToastProvider` but no longer the app shell. A route group `src/app/(app)/` adds `layout.tsx` (reads the member, renders `AppShell`) and `my-issues/page.tsx`. `src/app/sign-in/` has its own `layout.tsx` (the standalone centred signed-out layout) and `page.tsx` (form without a token, landing page with one). `src/app/not-found.tsx` renders inside the app shell itself, because the root layout no longer has it and unmatched addresses only render the root `not-found`. `src/app/page.tsx` is deleted: the Proxy always redirects `/` (Principle II).
- **Rationale**: route groups keep the shell off the signed-out page without a second root layout (`route-groups.md`); `not-found.tsx` may be an async server component (`not-found.md`).

## R19. Seed script (FR-033, NFR-001)

- **Decision**: start `scripts/seed.ts`, run as `npm run db:seed` on the development database: inserts the first admin (`owner@example.com`, "Owner Name", `owner`) and 14 more members (one deactivated, for RM-4), skipping rows that already exist (`ON CONFLICT DO NOTHING`), so it can be re-run. Sessions are not seeded (not useful: a seeded session's raw token would have to be printed to be used).
- **Rationale**: the roadmap asks each slice to add its data to the NFR-001 seed script; later slices append projects, issues and comments to the same script.

## R20. Tests (FR-032, DEC-005)

- **Decision**: unit tests (Node, real test database via RM-1's global setup) beside each server module and route; component tests (jsdom) beside each component. The `unit` project (the only one that uses the database) runs its test files one at a time (`fileParallelism: false` in `vitest.config.ts`, owner decision 2026-10-01), so no two database-backed files run together; this also stops RM-1's `src/server/migrations.test.ts`, which drops and recreates the `public` schema, from running while another database test file runs, and that file's `afterAll` restores the real schema (`drop schema if exists public cascade`, `create schema public`, then `applyMigrations(sql, path.resolve("migrations"))`, as the global setup does; tasks.md T088), so the files that run after it still find the RM-3 tables. The two together make database tests independent of file order. Database-backed tests still use unique emails, usernames and IP addresses per test, so tests in one file do not depend on each other's rows. `createFirstAdmin(sql, input)` owns its transaction (with the table lock), so tests never wrap it in a rolled-back transaction: the setup tests run against the test database and, before each test, delete and commit the rows they need gone in dependency order (`sessions`, `magic_links`, `sign_in_requests` and `sign_in_attempts`, then `members`), so `members` is committed-empty. The race test calls `createFirstAdmin` at the same time on two separate connections against that committed-empty table and asserts exactly one admin exists and the other call reports `Setup already done`. Email sending is replaced in tests by stubbing `fetch` (`vi.stubGlobal`), so no test reaches Resend or Mailpit. Proxy tests call the exported `proxy` function with a `NextRequest`.
- **Keyboard checks** (design.md "Keyboard and focus"): component tests use only the installed tools (React Testing Library's `fireEvent`; no `@testing-library/user-event`, Constitution IV). "Enter submits" means the field and the submit button are inside the same `<form>` and `fireEvent.submit(form)` sends the request. "Reached by the next Tab" or "in Tab order after" means DOM order checked with `compareDocumentPosition` (as `src/components/ui/FieldError.test.tsx` does), the element is focusable (not disabled, no `tabIndex={-1}`), and no element between the two has a positive `tabIndex`.
- **Coverage map**: REQ-004.1 to REQ-004.3, REQ-005.1 to REQ-005.5, REQ-006.1, REQ-006.2, SEC-001.1, SEC-001.2, SEC-003.1, SEC-007.1, OPS-006.1, REQ-003.4 (initials) and OPS-001.1/OPS-001.2 each get at least one named test; the full mapping is produced by `/speckit-tasks`.
- **OPS-006.1** (FR-032, CHK041): `src/server/env-files.test.ts` (RM-1) is extended with a test that: when a `RESEND_API_KEY` value is configured, runs `git grep --quiet --fixed-strings <value>` over the tracked files and expects no match (exit 1); when not configured (normal in local dev and npm test), skips that grep; in both cases, always asserts that the committed `.env.example`'s `RESEND_API_KEY` is empty or a placeholder (OPS-006: `.env.example` holds placeholders only).
- **Request-ID replay on `POST /api/sessions`** (FR-012, CHK029): besides the replay that signs in (same `requestId` and same token after a lost answer), a test sends a stored `requestId` with a wrong token (an unknown token, and another link that is already used) and asserts no `Set-Cookie` with a session value, no new or re-tokened session, and the normal-path answer `expired`. A stored `requestId` with a different valid, unused link answers `422`, creates no session and leaves that link unused. A session whose magic link was deleted still validates, and a repeat of its `requestId` and token answers `expired` with no session token. A repeat for a member deactivated after the first `signedIn` answers `expired`, not `signedIn`, and re-tokens no session.
