# Research: Project Foundation (RM-1)

Phase 0 output for [plan.md](./plan.md). Each entry: Decision, Rationale, Alternatives considered. Owner decisions Q1 to Q4 are resolved and recorded in plan.md, "Resolved owner decisions". No NEEDS CLARIFICATION remains.

## R1. Language, runtime and framework

- **Decision**: TypeScript on Node.js 24 LTS; Next.js 16 (App Router) with React 19; one Next.js project at the repository root serving pages, `/health` and the `/api/…` route handlers.
- **Rationale**: Section 12 fixes Next.js (TypeScript) on a single VPS. Node 24 runs `.ts` files directly (type stripping), so the project scripts run without a compiler or loader package. Type stripping only removes erasable syntax, so `tsconfig.json` sets `erasableSyntaxOnly` (TypeScript 5.8 or later) and `verbatimModuleSyntax` (type stripping keeps every import not marked `type`, so type-only imports must say `import type`), and `scripts/migrate.ts` and every file it imports (`src/server/config.ts`, `src/server/migrations.ts`) use `.ts` import extensions, erasable-only syntax (no enums, namespaces or parameter properties) and no path aliases. `tsconfig.json` also carries from the start what Next.js 16 forces or suggests (`target`, `lib: ["dom", "dom.iterable", "esnext"]`, `allowJs: true`, `skipLibCheck: true`, `strict: true`, `noEmit: true`, `esModuleInterop: true`, `module: "esnext"`, `moduleResolution: "bundler"`, `resolveJsonModule: true`, `isolatedModules: true`, `jsx: "react-jsx"`, `incremental: true`, the `next` plugin; `include: ["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts", ".next/dev/types/**/*.ts"]` and `exclude: ["node_modules", ".claude"]`, `.claude` because the main checkout's `.claude/worktrees/` holds full repository copies that `**/*.ts` would otherwise type-check, the same reason ESLint ignores `.claude/` in R6), keeping `strict`, `verbatimModuleSyntax` and `erasableSyntaxOnly`, so `next build` never rewrites it; the implementer confirms the final set by running a build (T023's `tsconfig.json`-unchanged check) (T002, T023). `allowJs` covers importing the untyped vendored `_ds_bundle.js` from `src/components/hairline.ts` (with a type declaration beside it if needed). One project keeps pages and API together.
- **Alternatives considered**: separate frontend and backend projects (two builds for one small app, against Principle I); Node 22 (older LTS, less complete type stripping).
- **Status**: packages approved (Q1).

## R2. Database, driver and schema changes

- **Decision**: PostgreSQL 18, installed locally (Homebrew `postgresql@18` or the official installer; no containers). Driver: `postgres` (postgres.js), which ships its own types. Schema changes are plain ordered SQL files in `migrations/`, applied by `applyMigrations(sql, folder)` in `src/server/migrations.ts`: it creates `schema_migrations` if missing, runs each pending file in name order in its own transaction together with its `schema_migrations` row, stops at the first failure and reports the failing file name. `scripts/migrate.ts` is the `db:migrate` command around it. `drizzle-orm` and `drizzle-kit` are requested in RM-3; drizzle-kit's generated SQL files then go into the same folder.
- **Rationale**: Meets the spec edge case ("left at the last fully applied version", "reports the failing change") literally, with no extra package; RM-1 has no table, so Drizzle would be unused (Principle II).
- **Alternatives considered**: Drizzle's migrator now (one transaction for all pending files, does not name the failing file, unused in RM-1); `pg` driver (needs `@types/pg`).
- **Status**: resolved (Q3).

## R3. Configuration and secrets

- **Decision**: One local file `.env.local`, git-ignored by the `.env*` and `!.env.example` rules. `.env.example` does not exist yet: T005 creates it with placeholders and it is committed. The `.gitignore` rules (`.env*`, `!.env.example`, `next-env.d.ts`, `/.next/`, `/node_modules`) already exist; T005 only verifies them. `next-env.d.ts` stays ignored because Next.js generates it with a comment that must not be committed (Constitution III). Settings: `DATABASE_URL` (development database) and `TEST_DATABASE_URL` (test database). Next.js loads `.env.local` itself; `scripts/migrate.ts` and `vitest.config.ts` load it with Node's built-in `process.loadEnvFile`. `src/server/config.ts` reads the settings and throws `Missing setting: NAME` for a missing or empty one, never echoing values. `src/instrumentation.ts` `register()` calls it at server start in the Node.js runtime through a dynamic import of `src/instrumentation-node.ts`, so the Edge bundle never sees `process.exit`; on failure it writes the message to standard error and exits with code 1. Both are unit-tested: `register()` exiting 1 on a missing or empty setting (FR-018), and `git check-ignore` showing `.env.local` ignored (exit 0) and `.env.example` not (exit 1, an expected result, not an error; `-v` is not used) (FR-017).
- **Rationale**: Built-in on both sides, so no dotenv package. The same mechanism serves the production server in RM-2 (OPS-006).
- **Alternatives considered**: `dotenv` (unneeded package); a JSON or TOML config file (needs parsing code; not loaded by Next.js).

## R4. Test tools (DEC-005)

- **Decision**: Vitest runs every automated test through `npm test`. `vitest.config.ts` defines two projects: `unit` (`src/**/*.test.ts`, Node environment) and `components` (`src/**/*.test.tsx`, jsdom environment, CSS Modules processed so computed styles can be read, through `css: { include: [/\.module\.css$/] }` in that project, since Vitest does not process CSS by default). Component tests use `render`, `screen` and `fireEvent` from `@testing-library/react` (with `@testing-library/dom` as its required peer) and plain Vitest assertions. Timing (300 ms, 5 s) uses Vitest fake timers; `fetch` is replaced with `vi.stubGlobal` per test. JSX is compiled by Vitest's built-in transform with the automatic runtime. Vitest globals are off, so Testing Library's automatic cleanup does not run; the `components` project's setup file `scripts/setup-components.ts` calls `cleanup` in `afterEach`.
- **Rationale**: One runner and one command for unit and component tests (DEC-005, section 12). Fake timers make the 300 ms and 5 s rules exact and fast.
- **Not used** (not approved, not needed): Playwright or any browser end-to-end tool (DEC-005); `@testing-library/jest-dom` (plain assertions such as `getAttribute` suffice); `@testing-library/user-event` (`fireEvent` covers click and input); `@vitejs/plugin-react` (the built-in transform compiles TSX).
- **Alternatives considered**: Node's built-in `node --test` (no DOM for component tests); Jest (needs a TypeScript transform; not DEC-005).
- **Status**: resolved (Q2).

## R5. Test database isolation

- **Decision**: `scripts/prepare-test-db.ts` is Vitest's global setup. Before each run it reads both `DATABASE_URL` and `TEST_DATABASE_URL` as loaded, before any test override, and refuses with `Missing setting: TEST_DATABASE_URL` when `TEST_DATABASE_URL` is missing or empty. `DATABASE_URL` is optional for `npm test` (tests need only `TEST_DATABASE_URL`); only when it is set does the guard check that `TEST_DATABASE_URL` names a different database from it (refusing otherwise): both are parsed with `new URL` and compared by host, port and database name, with `localhost`, `127.0.0.1` and `::1` treated as the same host and a missing port as `5432`, never as raw strings, drops and recreates the `public` schema of the test database, then runs `applyMigrations`. `vitest.config.ts` sets `DATABASE_URL` to `TEST_DATABASE_URL` only for the test worker processes through Vitest's `test.env`, never by assigning to `process.env` in the config file; inline projects do not inherit root `test` options by default, so both projects (`unit`, `components`) set `extends: true` and every worker gets the override (checked in T024), so the guard still sees both original values and code under test never reaches the development database. Only the migration runner's test changes the schema; it connects explicitly through `TEST_DATABASE_URL` and resets `public` itself before each case.
- **Rationale**: Meets FR-004 inside the one test command, with no extra tool; the equality guard stops an accidental wipe of the development database.
- **Alternatives considered**: a separate `db:test:prepare` command before `vitest run` (one more script to keep in step); a database per run (slower, more code); rolled-back transactions per test (does not cover the migration runner's own transactions).

## R6. Lint and build

- **Decision**: `npm run lint` runs `eslint . --max-warnings 0` with `eslint-config-next` (flat config: core web vitals and TypeScript rule sets, including React, hooks and accessibility). The config ignores `.next/`, `node_modules/`, `next-env.d.ts`, `.claude/` and the vendored `src/hairline/` (third-party files are not linted or patched; owner answers C1, C2). `.claude/` is ignored because a flat config does not read `.gitignore` and the main checkout's `.claude/worktrees/` holds copies of the repository. `--max-warnings 0` makes rule warnings such as unused variables fail the command. `npm run build` runs `next build`, which also type-checks, test files included.
- **Rationale**: Next.js 16 no longer ships `next lint`; the recommended config pulls in the rules that fit the stack.
- **Alternatives considered**: Biome (second toolchain not aligned with Next.js's rules); a hand-written ESLint config (more packages to approve). Principle III is a review check, not a lint rule.

## R7. Verifying shared screen states without a fixture page

- **Decision**: No test-only page or address ships in the app (DEC-005, Constitution II). Each shared state is proven by a component test that renders it directly:
  - Loading: nothing at 300 ms; at 301 ms a `role="status"` element with `aria-label="Loading"`; a `useLoad` that settles within 300 ms never shows it.
  - Empty: `EmptyState` shows "No issues yet. Create one." as plain text.
  - Load error: `useLoad` with a non-2xx answer or a rejected `fetch` shows "Couldn't load this." and Retry; Retry refetches while the state stays `"error"`, so `LoadError` never unmounts during a retry and a second failure keeps focus on Retry; success shows the content. Moving focus to the content after a successful retry is the host page's job and is not asserted here (owner answers U1, U2).
  - Field error: a Name field (Hairline TextInput) with Save in the test file; a `422` from `saveJson` shows "Enter a name." under the field with `aria-invalid` and `aria-describedby`, the typed text kept (focusing the invalid field is the host page's job and is not asserted, U1); wrapping is checked through the message's computed style (`overflow-wrap: anywhere`, no `white-space: nowrap`, no `text-overflow: ellipsis`) and the full text being present. Typed text also stays after a `500` or `403`, which show their toasts (T030).
  - Toast: "Couldn't save. Try again." and "You don't have permission to do that." appear in the `aria-live="polite"` region, stack in order, keep focus where it was, and each is gone 5 s after it appeared; wrapping is checked through computed style (`overflow-wrap: anywhere`) as for field errors.
  - Time: `LocalTime` for `02:00Z` reads "09:00" with the process zone set to `Asia/Bangkok` (UTC+7).
  - Not found: `not-found.tsx` inside `AppShell` shows the heading "Not found" and a "My issues" link to `/my-issues`; the heading takes focus after a client-side navigation only (R13). Routing every unmatched address to `not-found.tsx` with HTTP `404` is Next.js's own behavior, also checked by hand in quickstart.md.
- **Rationale**: FR-020 and SC-003 ask for component tests that render each state directly; jsdom has no layout engine, so line breaking and stacking positions are checked through their styles (CSS Modules reach jsdom through the `components` project's `css: { include: [/\.module\.css$/] }`, R4), and the frames in design.md remain the layout reference in review.
- **Alternatives considered**: a development-only fixture page (dropped by DEC-005); an HTTP test against a running `next start` (a build inside the test command, slow; closer to end-to-end testing, which DEC-005 excludes).

## R8. API convention and error shape

- **Decision**: All API routes live under `src/app/api/…/route.ts`, exchange JSON, use resource-style paths. Errors use one shape: `{ "error": { "message": string, "fields"?: { [field]: string } } }`. `apiRoute(handler)` in `src/server/api.ts` times the request, turns a thrown `ApiError(status, message, fields?)` into the error shape, turns any other throw into `500` `{ "error": { "message": "Something went wrong." } }` (no detail), and writes the log line. `src/app/api/[[...path]]/route.ts` (optional catch-all, so bare `/api` and `/api/` match too) answers every method with `404` `{ "error": { "message": "Not found" } }`. Create requests carry a client-generated `requestId` (UUID from `crypto.randomUUID()`) in the JSON body; RM-1 documents this only (contracts/http-api.md), because no create endpoint exists yet (FR-013). Route handlers are unit-tested by calling their exported functions with a `Request`.
- **Rationale**: One wrapper gives every later endpoint STD-1 to STD-4 answers, the log line and the `500` guard (FR-011, FR-012, FR-015). No validation library: RM-1 has no validated endpoint.
- **Alternatives considered**: Next.js `proxy` for logging (cannot see the response status); Zod (not needed yet).

## R9. Request logging

- **Decision**: `apiRoute` (also used by `/health`) writes one line per request to standard output: `{"time":"<ISO UTC>","method":"GET","path":"/api/x","status":200,"durationMs":12}`. The path comes from `new URL(request.url).pathname`, so the query string is never read into the log. Headers, cookies and bodies are never read by the logger. An unexpected error adds `{"time":…,"level":"error","method":…,"path":…,"error":"<error name>"}` (name only, no message or stack).
- **Next's own request log** (owner decision, 2026-10-01): turned off with `logging: { incomingRequests: false }` in `next.config.ts`, because it prints full URLs with the query string (seen leaking `?token=…`), which breaks FR-016.
- **Rationale**: FR-015, FR-016, SEC-007; the p95 read and write times (NFR-003) are computed by grouping on method.
- **Alternatives considered**: pino (a package for one `JSON.stringify` line); logging the error message (can carry database values).

## R10. Health check

- **Decision**: `src/app/health/route.ts` (`GET /health`, dynamic, no cache) runs `select 1` with an 800 ms time limit. Success: `200` `{"status":"ok"}`. Failure or time-out: `503` `{"status":"unavailable"}`. No detail. It goes through `apiRoute`, so it is logged. The check function takes the query as a parameter so unit tests pass a failing or hanging one.
- **Rationale**: FR-019, SC-004 (answer within 1 s even when the database hangs).
- **Alternatives considered**: the driver's connect timeout alone (whole seconds; too coarse).

## R11. Times (DATA-003)

- **Decision**: Every timestamp column is `timestamptz`, written in UTC (stated in AGENTS.md). `src/lib/time.ts` `formatTime(iso, timeZone)` uses `Intl.DateTimeFormat` with `hourCycle: 'h23'` and `HH:mm` output, falling back to `UTC` on a `RangeError` (invalid zone). `LocalTime` is a client component that renders `<time dateTime={iso}>` and fills its text after mount with the browser's zone, passing `UTC` when the resolved zone is missing or undefined so `Intl` never falls back to the host default, so the server's zone never shows and hydration never mismatches.
- **Rationale**: Built-in `Intl`, no date library; matches design open question 6.
- **Alternatives considered**: date-fns-tz or Luxon (packages); rendering on the server (wrong zone).

## R13. Not found focus: client-side navigation versus full page load

- **Decision**: `not-found.tsx` stays a Server Component and renders a small client child component, `src/app/NotFoundFocus.tsx`, next to the heading. On mount, the child compares `window.location.href` with the URL of the document's navigation entry (`performance.getEntriesByType("navigation")[0]?.name`). If they differ, the page was reached by a client-side navigation after the document loaded, and the child focuses the "Not found" heading (`tabIndex={-1}`). If they are equal, or there is no navigation entry, it is the initial full page load and focus stays at the browser default. The heading is referenced by id or a ref passed from the page. The component test (T025) simulates each case in jsdom by stubbing `performance.getEntriesByType`, with `vi.spyOn` when it exists, otherwise with `vi.stubGlobal` or `Object.defineProperty` (jsdom may lack it): returning an entry whose `name` equals `window.location.href` is a full page load (heading not focused); returning an entry with a different URL is a client-side navigation (heading focused).
- **Metadata**: `not-found.tsx` keeps its `metadata` export (title "Not found") only if Next.js 16 supports metadata on `not-found`. Support is expected but not certain here, so T032 verifies it against the Next.js 16 documentation during implementation; if it is not supported, T032 stops and asks the owner how the title "Not found · Tracklite" is set.
- **Rationale**: design.md, Keyboard and focus: the heading takes focus after an in-app navigation, not on a full page load (owner answer U3). The navigation entry is a browser built-in, so no router internals or extra layout component are needed.
- **Alternatives considered**: reading Next.js's internal `history.state` (private, may change); a module-level "first render" flag (cannot tell a first visit by client-side navigation from a full load). Known limit: a client-side navigation back to the exact URL the document was loaded with counts as a full load.
