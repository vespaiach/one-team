## R1. Server, accounts and size

- **Decision**: One Hostinger VPS with Ubuntu 24.04 LTS, Node.js 24 LTS (NodeSource apt), PostgreSQL 18 (PGDG apt, `localhost` and Unix socket only) and Caddy 2 in front. Two accounts matter: the owner's admin account (SSH key, `sudo`) and the `tracklite` system account, which owns `/srv/tracklite`, runs the app, and is the account the deploy and rollback commands log in as (SSH key only). A sudoers drop-in lets `tracklite` run exactly `systemctl start` and `systemctl stop` on `tracklite@<release id>.service` units, matched by a sudoers regular expression (sudo 1.9.15 on Ubuntu 24.04 supports `^…$` patterns), and nothing else. `ufw` allows 22, 80 and 443 only. PostgreSQL has a role and database named `tracklite`; the app connects over TCP with the password in `DATABASE_URL`, and the scripts that run on the server as the `tracklite` account (backup, slot check) connect over the Unix socket with peer authentication, so no password ever appears on a command line.
- **Size check for two app processes side by side** (spec Assumptions, FR-004): measured on 2026-10-01 from this repository: `next build` peaks at about 1.35 GB resident memory; one `next start` process holds about 125 MB after 100 requests (macOS arm64; Linux x64 assumed 150 to 250 MB). Estimate on the server:

  | Phase | Live app | New app | PostgreSQL 18 (defaults) | Caddy | OS, sshd, journald | `next build` | Total |
  |-------|----------|---------|--------------------------|-------|--------------------|--------------|-------|
  | Building the new release | 0.25 GB | — | 0.25 GB | 0.05 GB | 0.25 GB | 1.35 GB | about 2.2 GB |
  | Two versions side by side (start → switch → old drained) | 0.25 GB | 0.25 GB | 0.25 GB | 0.05 GB | 0.25 GB | — | about 1.1 GB |

  The side-by-side window needs about 1.1 GB, which fits in 2 GB. The build is the larger peak (it existed in the old design too): on a 2 GB plan it needs the 2 GB swap file, on a 4 GB or larger plan it fits in memory. Disk: one full release is about 0.6 GB (`node_modules` 554 MB plus `.next`); at most four exist in full at once (live, previous slot, the release switched away from, the one being built), about 2.4 GB of 40 GB, plus the `.next/static` folders kept for up to 5 earlier releases (a few MB each, R3). **Outcome: the decided size (2 vCPU, ≥ 2 GB RAM plus a 2 GB swap file, ≥ 40 GB disk) fits two app processes during a switch; no larger plan is needed and NFR-009 is unaffected (R11).** Hostinger's smallest 2-vCPU plan is assumed to have more than 2 GB (to confirm on its price page); the swap file stays in the setup either way.
- **Memory pressure during a deploy** (Edge Cases, Clarifications): the deploy's own work is made the kernel OOM killer's first choice, with no root and no new software. The worker writes `1000` to its own `/proc/self/oom_score_adj` before any step, so `npm ci`, `next build` and the migration runner inherit it; right after starting the new instance (deploy) or the rollback target, it writes `1000` to that instance's `/proc/<MainPID>/oom_score_adj` (`systemctl show -p MainPID --value`; the instance runs as `tracklite`, and raising the value needs no privilege). The live instance keeps the default `0`, and PostgreSQL keeps the `OOMScoreAdjust=-900` that postgresql-common's `postgresql@.service` sets (`docs/production.md` has the owner confirm it with `systemctl show -p OOMScoreAdjust postgresql@18-main`), so both rank below any deploy work. Right after the switch the worker writes `0` back to the new live instance (allowed unprivileged, because systemd started it with the default and so its lower bound is `0`); if that write fails it is a post-switch problem, reported as a warning (R4), and a restart or a boot starts every instance at `0` anyway. Each run's cleanup first writes `0` to the live instance's `/proc/<MainPID>/oom_score_adj` (when `current` exists), resetting any `1000` left by an earlier failed reset; if that write fails, the run fails (`oom_score_adj reset`, exit 1) before any deploy or rollback work. When the live instance has no running process (`systemctl show -p MainPID --value` is `0`: it crash-looped past systemd's restart limit, or was stopped by hand), there is nothing to protect, so the reset is skipped and the run continues; `oom_score_adj reset` fails a run only when a running live process exists and the write to it fails. A deploy or rollback can therefore always replace a live release that is down (R2, "Live instance not running"). If the kernel kills the build, the install or the migration runner, that step fails (`install`, `build`, `migration <file>`); if it kills the new instance (or a rollback target), the run fails with `start`; either way before switching, the live release untouched. The unit's `Restart=on-failure` (contracts/commands.md "App units") would bring a killed instance back at `oom_score_adj` `0`, where it might pass `/health`; so the worker records the instance's `MainPID` right after starting it, rereads it at every `/health` poll and immediately before the rename, and fails with `start` when it is `0` or has changed. A restarted candidate is thus never switched to, and the live instance keeps `Restart=on-failure`, with no per-instance unit change and no sudo rule beyond `start` and `stop`. The worker's own Bash process uses a few MB, so the OOM killer, which ranks by `oom_score_adj` and then by memory used, picks the build or the new instance first.
- **Rationale**: Section 12 fixes one VPS with the database on it. Logging in as `tracklite` avoids a password prompt (SC-001) without giving the deploy root. The regular-expression sudoers rule closes the classic hole where a `*` wildcard also matches extra unit names after a space.
- **Alternatives considered**: deploying as the admin account (password prompt or passwordless root); `tracklite` user-level systemd with lingering (no sudo, but no ordering after `postgresql.service` and logs split into a per-user journal); containers (RM-1 chose none).

## R2. Releases, the `current` symlink and the atomic switch

- **Decision**: Each release is prepared completely in its own directory `/srv/tracklite/releases/<id>/`, `<id>` = UTC deploy start `yyyymmddTHHMMSSZ` plus `-` plus the 7-character commit, never changed after it is prepared except for its two port files (below). Two symlinks in `/srv/tracklite/` name the slots: `current` (the live release, FR-005) and `previous` (the single previous-release slot, FR-008; absent when empty). The **atomic switch** is one `rename(2)` of `current`: `ln -s releases/<id> current.next && mv -T current.next current`. That rename is the commit point of every deploy and rollback (Clarifications). Release states and every transition are in [data-model.md](./data-model.md).
- **How two versions run side by side**: a release gets its port, `3001` or `3002`, each time it is started before a switch (the new release of a deploy, or the rollback target), as the one the live release does not use, written into the release as `release.env` (`PORT=…`) and an empty marker file `port-3001` or `port-3002` (the other marker removed). These two files are the only ones ever rewritten in a prepared release, and only while it is not live and its instance is stopped, so Caddy, which reads only `current/port-3001`, never sees them change. Choosing the port at start, not at preparation, keeps rollback working after a redeploy of the live commit, which leaves the previous-release slot holding a release whose last port may equal the new live one's (R2, deploy order). Each release runs as its own instance of one systemd template unit, `tracklite@<id>.service` (`WorkingDirectory=/srv/tracklite/releases/%i`, `EnvironmentFile=/etc/tracklite/env` and `…/%i/release.env`, `ExecStart=…/%i/node_modules/.bin/next start --hostname 127.0.0.1`; `next start` reads `PORT` from the environment). `next start` listens only on a TCP host and port (Next.js 16 CLI docs: `-p/--port`, `-H/--hostname`, no socket option), which is why the two versions are told apart by port.
- **How traffic follows the symlink**: Caddy decides the upstream for every request with a single `file` matcher that checks whether `/srv/tracklite/current/port-3001` exists: if it does, the request goes to `127.0.0.1:3001`, otherwise to `127.0.0.1:3002` (R5, [contracts/https-front.md](./contracts/https-front.md)). Each request is routed by one file-system lookup through `current`, so it sees either the old or the new target of the rename, never a mix, and the switch moves traffic the instant the rename happens, with no Caddy reload. One check, not one per port: two separate checks could straddle the rename and match neither.
- **Deploy order** (server side, under the lock, R4): raise the worker's `oom_score_adj` (R1) → clean up leftovers (first write `0` to the live instance's `oom_score_adj`, R1, skipped when the live instance has no running process, failing the run with `oom_score_adj reset` if a running live process exists and that write fails; stop every `tracklite@` instance except the live one; delete every `incoming/` directory other than this run's own that was last modified more than 60 minutes ago, R4; prune releases, R3) → check free disk space: below one full release plus the build's headroom, about 3 GB (an estimate: about 0.6 GB for the release, R1, plus room for `npm ci` caches and `next build` output, to confirm on the first deploys), fail with `disk space`, nothing changed → extract the uploaded commit into a new release directory → `npm ci` → `NEXT_DEPLOYMENT_ID=<id> next build` (R3) → apply schema changes with the server config file → write the new release's port files, start `tracklite@<new>` beside the live one, record its `MainPID` and raise that process's `oom_score_adj` → poll `http://127.0.0.1:<new port>/health` every 2 s, each try limited to 2 s, for up to 60 s (FR-004), checking at each poll that `MainPID` is still the recorded one (otherwise fail with `start`, R1) → on `200`: check `MainPID` once more (same rule), record `switching <old> → <new>`, rename `current` (commit point), append the new id to the live history (R3), set `previous` to the old release unless the new release has the same commit as the old one (a redeploy of the live commit is a full deploy that leaves `previous` as it was, FR-008), reset the new instance's `oom_score_adj`, wait 2 s for requests already routed to the old port to reach it, then `systemctl stop tracklite@<old>`: SIGTERM, on which `next start` finishes in-flight requests before it exits (Next.js self-hosting guide), with `TimeoutStopSec=30`, so every request in progress at the switch has at least 30 s from the switch to finish (FR-005; the old instance is killed at the latest 32 s after the switch) → record the end. On any failure before the rename: stop the new instance if started, apply the slot rule (R2a), record the failure; the old release was never touched (FR-003, FR-004).
- **After the commit point** nothing can change the outcome (FR-007): if the old instance had to be killed at its stop limit (`systemctl show -p Result` is `timeout`), a leftover could not be removed, the `oom_score_adj` reset failed, or the run record could not be written, the run is still `succeeded`, exits 0 and prints one `Warning: <problem>` line per problem; leftovers go at the next run's cleanup. A run whose end could not be recorded is closed by the next command as `interrupted`, naming the new live release (R2b).
- **Rollback order**: refuse with "nothing to roll back to" if `previous` is absent (FR-010) → refuse with "database could not be checked", exit 2, slot unchanged, if the S2 check (R2a) could not read `schema_migrations` → raise the worker's `oom_score_adj` and clean up leftovers as for a deploy (live instance's `oom_score_adj` reset first; leftover non-live instances stopped in parallel, at most 30 s in total; deleting and pruning release directories, R3, is left until after the switch) → write the target's port files, start `tracklite@<previous>`, record its `MainPID` and raise its `oom_score_adj` → same `/health` wait and `MainPID` checks (a changed or `0` PID fails with `start`) → record `switching`, rename `current` to the previous release (commit point), append it to the live history, remove `previous`, reset its `oom_score_adj`, wait 2 s, stop the old instance (same 30 s drain), then delete and prune release directories (R3) as the cleanup would have before the switch, keeping the release switched away from whole (a failure is a `leftover not removed` warning; after a rollback that fails before its switch, the next run's cleanup does it). No build and no database step: cleanup (at most 30 s) + start (a few seconds) + at most 60 s of `/health` wait stays under 2 minutes, measured from running the command to the switch (SC-003); the drain after the switch doesn't count. A rollback whose target fails to start (including exiting or being restarted before the switch) or fails `/health` stops the target instance and changes nothing else; the slot still holds the target (FR-008, FR-009).
- **Live instance not running** (`current` exists but `tracklite@<current>` has `MainPID` `0`, for example after a release crash-looped past systemd's restart limit or was stopped by hand): deploy and rollback run exactly as above. The cleanup skips the `oom_score_adj` reset (R1); the new instance or rollback target still starts on the port `current` does not use and must pass the same `/health` wait and `MainPID` checks on its own port, which never depend on the old instance; the switch is the same rename. There is nothing to drain: the 2 s wait and `systemctl stop tracklite@<old>` still run, the stop of an inactive or failed unit returns at once and succeeds, and no `old instance killed after 30 s` warning can arise. If the new instance or target fails before the switch, the run fails as usual and `current` still names the stopped release (FR-004 and FR-009 "untouched": it is left as it was, not started). Members get Caddy's `502` until the switch, as they already did, so there is no zero-downtime claim to keep for that window.
- **R2a. Previous-release slot after a failed or interrupted deploy** (FR-008, Clarifications): rather than tracking which steps ran, the scripts enforce one invariant read from durable state: *if the database's `schema_migrations` table names any migration that is not a file in the live release's `migrations/` folder, the `previous` slot must be empty.* After a successful deploy every applied migration ships with the live release, so the slot is kept; a failed or interrupted-before-switch deploy that applied any migration leaves a row the live release does not ship, so the slot is emptied; one that applied none leaves the slot as it was. After a rollback the slot is already empty. Migration files are never renamed or deleted once applied (AGENTS.md), so the check cannot misfire. It reads the table with `psql -d tracklite` over the Unix socket (peer authentication, no secret). The check is skipped only when `current` is absent or `schema_migrations` doesn't exist; if `psql` fails otherwise, the slot is left unchanged but not trusted: a rollback refuses with `Refused: database could not be checked`, exit 2, and works again once the check can run (FR-009). A deploy whose start-of-run check fails this way carries on with the slot unchanged: its migration step needs the database anyway and fails cleanly (`Deploy failed: migration …`) if it is truly down, and the rollback's own check guards the slot later (Clarifications). The same holds for the check a failed or interrupted deploy runs at its end: if it cannot read `schema_migrations`, the slot is left unchanged and the rollback's own check guards it. This needs no change to RM-1's `scripts/migrate.ts`, which applies each file in its own transaction and records it in `schema_migrations` in that same transaction.
- **R2b. Interrupted runs**: every run writes a run record (data-model.md) before it acts, including `switching <from> <to>` immediately before the rename. A run that died, or whose end could not be written, has no `ended` line; the next command finishes its bookkeeping under the lock. Before anything else it kills the dead run's whole process group, `kill -KILL -- -<session>` with the `session` id from the run record (skipped when the record has none, or no process of that group remains): a killed worker's children (`npm ci`, `next build`, `scripts/migrate.ts`) are not killed with it and would otherwise keep running beside the new run (FR-006). Linux never reuses a PID still in use as a process-group or session id, so the kill cannot reach an unrelated process; the app instances are started by systemd in their own cgroups and are not in the group. Then, for a deploy, if `current` already points at `<to>` the switch committed, so `previous` is set to `<from>` as after a success (left as it was when `<from>` and `<to>` have the same commit, a redeploy) and `<to>` is in the live history; otherwise the R2a invariant is applied. For a rollback, if `current` points at the target, `previous` is removed and the target is in the live history (as after a success); otherwise nothing changes. In both cases the record is closed as `interrupted`, any instance other than the live one is stopped, and the live one is started if it is not running.
- **Boot**: `tracklite@` instances are not enabled. A one-shot unit `tracklite-boot.service` (enabled, after `postgresql.service`) starts the instance `current` points at, so after a reboot the live release is whatever `current` says, with nothing else to keep in step. Caddy needs no state either: it reads `current` on every request.
- **Rationale**: The rename of one symlink is the only atomic switch the file system offers, and letting Caddy look through that symlink on each request makes the symlink itself the traffic switch, as the user's "symlink deployment" mandate asks, with no second piece of state (a Caddy config, an enabled unit) that a dying run could leave out of step. Fixed alternating ports are the smallest way for two `next start` processes to coexist.
- **Alternatives considered**: switching by `systemctl reload caddy` with an upstream file imported through `current` (a second state that can disagree with the symlink if the run dies between rename and reload, and a reload that can fail after the commit point); a Caddy admin-API upstream change (same split state, and the admin API is writable by any local user); Unix sockets per release behind a socket symlink (`next start` cannot listen on a socket without a custom server, which is application code); stop-then-start with one unit (the superseded design: a gap and errors during every deploy); PM2 or a deploy tool such as Kamal or Capistrano (new software needing approval, more than this needs); `git pull` in place (mixes files of two commits).

## R3. Building on the server, and version skew

- **Decision**: The deploy command uploads `git archive <sha>` (exactly the committed tree, no `.env.local`), and the server runs `npm ci` and `next build` in the new release directory with `NEXT_TELEMETRY_DISABLED=1` and `NEXT_DEPLOYMENT_ID=<release id>`, and without the server config file loaded. `NEXT_DEPLOYMENT_ID` is Next.js's built-in deployment identifier, set by environment variable at build time, so `next.config.ts` does not change: pages from a release carry its id, static file URLs get `?dpl=<id>`, and a browser holding a page from the old release that navigates after the switch gets a full page load from the new release instead of a mixed client-side navigation (Next.js 16 `deploymentId` and "Version skew" docs). Caddy serves `/_next/static/*` requests that carry `?dpl=<id>` from that release's own `.next/static/` folder when the file exists there, so a page keeps loading its own release's scripts and styles across later switches (R5). **Static files of the last 5 releases** (FR-005, Clarifications): `/srv/tracklite/live-history` lists release ids in the order they became live, one per line, appended right after each committed switch (or by the next command for a run that died after its switch, R2b). The cleanup at the start of each run keeps `current` and `previous` whole, keeps only the `.next/static/` folder (at its usual path, so the `dpl` handling is unchanged) of the 5 most recent distinct ids in the history other than `current`, deletes every other release directory, and trims the history to those ids. A page from any release live during the last 5 switches therefore still loads its own files. A release pruned to `.next/static/` has no `node_modules` or server build, so it is never started and never a rollback target; only `previous` is (FR-008). Between runs the release just switched away from is still whole (it is pruned at the next run's cleanup).
- **Rationale**: The build needs Linux-native binaries (Next's SWC, Tailwind 4's `@tailwindcss/oxide`, `lightningcss`), so a Mac build cannot be copied. Building without the config file guarantees no secret is inlined (FR-024); RM-1 has no `NEXT_PUBLIC_` variable and every settings-reading route is dynamic. The deployment id and the per-release static files are what keep a browser from getting a missing-file error or a mixed navigation across the switch (FR-005, SC-010). **Stop condition**: if `next build` turns out to need a setting, implementation stops and asks rather than loading the config file into the build.
- **Alternatives considered**: building locally for linux-x64 (native optional dependencies install for the host platform); `output: "standalone"` (changes `next.config.ts` and the start command for no requirement); `deploymentId` in `next.config.ts` (the environment variable does the same with no app change); a shared folder accumulating every release's static files (needs its own pruning rule); no skew handling (an open tab's next script request after the switch would be a `404` caused by the switch).

## R4. Deploy and rollback commands, the lock and runs that outlive the connection

- **Decision**: `npm run deploy` runs `scripts/deploy.sh`, `npm run rollback` runs `scripts/rollback.sh` (Bash, owner's machine). `deploy.sh` first checks, without contacting the server: on `main`; `git status --porcelain` empty; `git fetch origin main` succeeds (otherwise "the shared main couldn't be checked", FR-002, Clarifications); `HEAD` equals `origin/main`. It then uploads the commit's `git archive` and its `ops/release.sh` into a directory of its own, `/srv/tracklite/incoming/<random id>/` (`<random id>` generated locally per invocation, 16 hex characters read from `/dev/urandom`; files written under temporary names, then `mv`), and runs `bash /srv/tracklite/incoming/<random id>/release.sh deploy <sha>` over SSH (the uploaded copy has no execute bit, so it is always run through `bash`) (host alias `tracklite`). Each run uses only its own directory, so two invocations never overwrite each other's upload; these directories are the only files written before the lock, and each run's cleanup under the lock deletes every `incoming/` directory other than its own whose modification time is more than 60 minutes old (`find /srv/tracklite/incoming -mindepth 1 -maxdepth 1 -type d -mmin +60`). An upload takes seconds and ends with the `mv` that sets its directory's modification time, so a directory still being uploaded, or uploaded but not yet run, by a concurrent invocation is never deleted: two deploys started together both find their own script, and the one that reaches the lock second is refused with "a deploy is running", exit 3 (FR-006), not an upload failure. Directories younger than 60 minutes, such as a refused invocation's, are left for a later run's cleanup. Only an invocation whose upload-to-SSH gap exceeded 60 minutes could find its directory gone; it then finds no script and reports `Deploy failed: upload`, exit 1, nothing else changed. Any SSH connection failure after the upload (`ssh` exit status 255; `release.sh` itself only exits 0 to 4) is mapped by the local script to exit 4, and the script always prints the connection-lost message itself (contracts/commands.md). `rollback.sh` has no local checks and runs `bash /srv/tracklite/current/ops/release.sh rollback` (the live release's copy). With no `current` (nothing live yet) it runs `bash` on the most recently written `/srv/tracklite/incoming/*/release.sh` with `rollback` instead: while nothing is live every run past the lock was a deploy, and a run's cleanup never deletes its own `incoming/` directory, so the last such deploy's copy is still there whenever a run record exists. Its front then behaves as for any rollback: it takes the lock, prints the unreported outcome first (`… nothing is live yet`), and refuses with "nothing to roll back to" because `previous` is absent (FR-007, FR-010). Only when no copy exists at all, which means no run ever got past the lock and nothing can be unreported, does the remote command print "nothing to roll back to" without running `release.sh`.
- **Server side, one script `ops/release.sh`**, two roles:
  1. **Front** (attached to the SSH session): opens `/srv/tracklite/release.lock` and tries `flock -n`. Right after `flock -n` succeeds, it writes `deploy` or `rollback` into `release.lock`. If the lock is held: print any recorded but unreported outcome of an earlier run, then refuse with "a deploy is running" or "a rollback is running", read from the lock file, exit 3 (FR-006). If the lock is free: finish the bookkeeping of a run that died (R2b) and print "the last deploy/rollback was interrupted; `<release id>` is live" (release ids as in data-model.md; `nothing is live yet` when `current` is absent), or print the unreported recorded outcome of a run that ended; mark it reported (FR-007). For rollback, refuse if `previous` is absent, or with `Refused: database could not be checked` (exit 2, slot unchanged) if the S2 check (R2a) could not read `schema_migrations`. Then create the new run record and start the **worker** with `setsid` (new session, standard input from `/dev/null`, output appended to the run's log file), passing it the open, locked file descriptor, and close its own copy. It then follows the log (`tail --pid=<worker>`) to the owner's terminal, marks the record reported, and exits with the run's status: the recorded outcome, or, when the worker ended without recording one, `0` with a `Warning: run record not written` line if `current` names the run's target (commit point passed), else `1` with `Deploy failed: interrupted; <live release id> is live` (or `Rollback failed: …`). A record it cannot mark reported stays unreported, so the next command prints it again; for a record without an end the next command reports `interrupted` (FR-007).
  2. **Worker** (detached): does the deploy or rollback of R2 and writes its outcome to the run record. The lock is held by the worker's inherited file descriptor, so it lives exactly as long as the worker: the kernel frees it when the worker ends or dies, including on a server restart (FR-006: never stuck). The worker runs every child command (`npm ci`, `next build`, the migration runner, `curl`, `sudo systemctl`) with that descriptor closed, so an orphaned child of a killed worker cannot keep the lock. The worker records its session id in the run record (data-model.md `session`) before it starts any child, and runs without job control (no `set -m`), so every child stays in its process group; an orphaned child can therefore still be found and killed by the next command (R2b). Because the worker is in its own session with no terminal, a dropped SSH connection only ends the front; the worker continues to the end and records its outcome (FR-005), which the next command prints (FR-007).
- **Order of "first print the unreported outcome"** (FR-007, Clarifications): "first" means the first thing printed once the command reaches the server, that is, the first output of `release.sh`. The local refusal checks of FR-002 and the upload run before that and print no earlier outcome: a local refusal or an upload failure leaves it unreported until a command reaches the server. Every other refusal, including a rollback's "nothing to roll back to" while nothing is live, is made by the front after it has printed the outcome.
- **Rationale**: Bash and util-linux (`flock`, `setsid`, `tail --pid`) are on every Ubuntu server, need no approval, and give exactly "lock tied to a live process" and "run survives the connection". Handing the locked descriptor from front to worker leaves no window in which a second command could slip in. The script ships with the commit it deploys, so deploy logic never drifts from the code.
- **Alternatives considered**: `systemd-run` transient units for the worker (survives too, but needs a sudo rule for arbitrary `systemd-run` arguments); `nohup` alone (stays in the SSH session's process group); a lock file holding a PID (can be left stale after a crash); `tmux`/`screen` (new software, interactive); TypeScript scripts (would only shell out to the same commands).

## R5. HTTPS front server: Caddy

- **Decision**: Caddy 2 (official apt repository; approved, Q2) with one site block for the team's domain, committed as `ops/Caddyfile`: automatic Let's Encrypt certificate and renewal (FR-012, FR-015) and automatic permanent redirect of every `http://` request to the same path and query on `https://` (FR-013); `header Strict-Transport-Security "max-age=31536000"` on every response, no `includeSubDomains`, no `preload` (FR-014); `/_next/static/*` with `?dpl=<id>` served from `/srv/tracklite/releases/<id>/.next/static/` when that file exists (the live release, `previous`, and the static folders kept for up to 5 earlier releases, R3), with `Cache-Control: public, max-age=31536000, immutable`, otherwise passed to the live app; everything else routed by the single `file` matcher on `/srv/tracklite/current/port-3001` to `127.0.0.1:3001` or `127.0.0.1:3002` (R2). No site-level `log` directive (no access log); errors go to the journal through a global error-log filter that keeps method, path without query string, status and error (R9, FR-025, FR-026). Caddy's `file` matcher joins the requested path to its root with path cleaning, so a crafted `dpl` value cannot leave `/srv/tracklite/releases/`, and release trees hold no secrets (R6).
- **Rationale**: One config file covers certificates, renewal, redirect, HSTS and the per-request switch; Caddy evaluates `file` matchers on each request, which is what makes the symlink rename the switch. **Stop condition**: if a trial (quickstart §5) shows Caddy caching the `file` matcher's lookup across requests, implementation stops and asks before choosing a different switch.
- **Alternatives considered**: nginx with certbot (two components, a renewal timer, a hand-written redirect; nginx resolves `root` symlinks per request too but would need an approval); HSTS in `next.config.ts` (the redirect still needs a front server); Cloudflare's proxy (ties HTTPS to a third party; the owner decided proxy off).

## R6. Server config file

- **Decision**: One file, `/etc/tracklite/env`, owned `root:tracklite`, mode `0640` (FR-023). `NAME=value` lines, read by systemd's `EnvironmentFile=` and by `node --env-file`. Keys: `DATABASE_URL` (app and migrations) and the backup storage settings `BACKUP_REMOTE` plus `RCLONE_CONFIG_BACKUP_*` (R7). Every `tracklite@` instance and `tracklite-backup.service` load it; the deploy runs migrations with `node --env-file=/etc/tracklite/env scripts/migrate.ts` in the new release. Every release reads the same file and none contains it (FR-024). The app keeps reading settings through RM-1's `readSettings()`.
- **Rationale**: Same environment-variable mechanism as RM-1; one file for every secret.
- **Alternatives considered**: `.env.local` per release (deploy would copy secrets, against FR-024); a secrets manager (cost and a dependency).

## R7. Daily off-server backups

- **Decision**: `tracklite-backup.timer` (`OnCalendar=*-*-* 03:00:00 UTC`, `Persistent=false`) starts `tracklite-backup.service` (as `tracklite`, config file loaded), which runs `/srv/tracklite/current/ops/backup.sh`: `pg_dump --format=custom --dbname=tracklite` over the Unix socket into a temporary file (one snapshot in one transaction, so consistent even while a deploy applies schema changes) → `rclone copyto` to `$BACKUP_REMOTE/tracklite-<yyyy-mm-ddTHH-MM-SSZ>.dump` → `rclone lsf`, sort by name, delete everything beyond the 14 newest → remove the temporary file. `set -euo pipefail`, so a failure stops before any deletion (FR-017, FR-018). Cloudflare R2 (Q1) through rclone's S3 backend configured only by `RCLONE_CONFIG_BACKUP_TYPE=s3`, `_PROVIDER=Cloudflare`, `_ENDPOINT=https://<account id>.r2.cloudflarestorage.com`, `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY` (an R2 token scoped to the backup bucket). No on-demand command; trials start the service directly (Clarifications).
- **Rationale**: `pg_dump` matches the server; rclone covers upload, list and delete; R2 is a different company from the VPS provider; a restore needs only the R2 account and `pg_restore` (FR-019).
- **Alternatives considered**: `curl --aws-sigv4` (XML listing in Bash); the AWS CLI (larger); bucket lifecycle rules (cannot express "keep 14, delete only after a successful new one"); WAL archiving (beyond OPS-003).

## R8. Logs and rotation

- **Decision**: All app, backup and Caddy output goes to the systemd journal; a journald drop-in sets `Storage=persistent`, `MaxFileSec=1day`, `MaxRetentionSec=14day` (FR-025, SC-008), and no `SystemMaxUse`, so journald's default size cap stays. journald deletes a whole archived day file only once its newest entry passes 14 days, so entries up to about 15 days old can remain; SC-008 therefore checks that nothing in the journal is older than 15 days and that each of the last 14 days is present. The retention is server-wide: it applies to every log in the journal, including system and SSH logs, not only the app's. Ubuntu 24.04 also writes plain log files outside the journal: rsyslog's `/var/log/syslog`, `auth.log` (SSH), `kern.log`, `ufw.log` and the others listed in `/etc/logrotate.d/rsyslog` (logrotate default about 4 weeks), and PostgreSQL's `/var/log/postgresql/*.log` (`/etc/logrotate.d/postgresql-common`, about 10 weeks). A one-time setup step in `docs/production.md` (T037) edits those two logrotate configs to `daily` and `rotate 14` (no new software; logrotate already runs daily from `logrotate.timer`), so the current file plus 14 rotated ones also stay within the same 15-day/last-14-days rule as the journal. PostgreSQL's server log would otherwise hold row data: by default a constraint violation adds a `DETAIL:` line with the key or the whole failing row, and every error adds a `STATEMENT:` line with the statement and its values. The same setup step (T008, documented again in T037) sets `log_error_verbosity = terse` (no `DETAIL`, `HINT`, `QUERY` or `CONTEXT` lines) and `log_min_error_statement = panic` (no failing statement logged) in `/etc/postgresql/18/main/postgresql.conf`, applied by a reload and checked with `SHOW`; both are superuser-only settings, so the `tracklite` role cannot override them (FR-026). A quickstart §11 trial triggers one constraint violation and checks the log. `docs/production.md` has the owner check `journalctl --disk-usage` during the SC-008 period, to see that the default cap does not delete logs before 14 days. Both app instances of a switch log to the same journal (`journalctl -u 'tracklite@*'`), so the log continues without a gap across deploys and rollbacks (US6 scenario 4). Deploy and rollback run records and run logs (R4) are files under `/srv/tracklite/runs/`, outside the journal and outside SC-008/FR-025's 14-day log rule: each run prunes run files older than 14 days at its start, so they are pruned at the next run, always keeping the newest record (which may still be unreported); they hold no secrets (FR-026).
- **Rationale**: One rotation mechanism for everything the server logs; content unchanged from RM-1.
- **Alternatives considered**: files plus logrotate for the app's own output (two mechanisms for the app); removing rsyslog so everything stays in the journal (changes the base system); a hosted log service (cost; request logs off-server).

## R9. Keeping secrets out of output (SEC-007, FR-026)

- **Decision**: No `set -x`; no environment values printed; no secret on any command line (`DATABASE_URL` reaches Node through `--env-file`, `psql` and `pg_dump` use peer authentication, rclone reads its keys from the environment). Messages name steps, commits and file names only. `npm ci` and `next build` run without the config file. Caddy keeps no access log; RM-1's request log already holds no query strings, headers, cookies or bodies. Caddy's error log lines (for example a `502` while no app answers) would otherwise carry the request's full URI and headers, so `ops/Caddyfile` sets a log filter on its error log that keeps only the method, the path without the query string, the status and the error, and deletes every other `request>…` field (the query string from `request>uri`, and `request>remote_ip`, `remote_port`, `client_ip`, `proto`, `host`, `headers`, `tls` and any other present) (FR-026); a quickstart §10 trial checks a fake token sent in the query string during a `502` never reaches the journal.
- **Alternatives considered**: filtering output for secret values afterwards (fragile).

## R10. External uptime check

- **Decision**: Better Stack Uptime, free tier (Q1): `https://<domain>/health` every 5 minutes, about 10 s time limit, failure = non-`200`, no answer or time-out, email the owner after the second consecutive failure, none for a single failure followed by a pass (FR-020 to FR-022). Settings documented in `docs/production.md`. During a deploy or rollback the check keeps getting `200` from the live release (FR-005), so deploys raise no alert. **Stop condition**: if the free tier cannot both check every 5 minutes and alert only after two consecutive failures, implementation stops and asks; the fallback is another hosted monitor whose free tier does (for example UptimeRobot), or a paid tier only if the total stays within NFR-009.
- **Alternatives considered**: a check on the VPS itself (cannot alert when the VPS is down); a self-hosted monitor elsewhere (cost, another machine).

## R12. Automated checks and the FR-011 review rule

- **Decision**: OPS-002 to OPS-005 and SEC-005 are "Verify: ops", checked by the trials in [quickstart.md](./quickstart.md). One Vitest test is added beside RM-1's `src/server/env-files.test.ts`: `git ls-files` lists no settings file (`.env*`, `*.env`) other than `.env.example` (OPS-006.1). FR-011 is checked in pull-request review (Clarifications): a new `.github/pull_request_template.md` asks every pull request that adds a file under `migrations/` to state why it keeps working with the code actually live in production when it will be applied (`/srv/tracklite/current/REVISION`), which is the previous release one step back, or, after a rollback, the release two back, in which case the statement says so (FR-011, Clarifications). AGENTS.md's migration convention says the same. This matches invariant S2 (data-model.md), which also compares against the live release's migrations.
- **Rationale**: Vitest runs in Node and jsdom only (DEC-005); SSH, systemd and Caddy behavior cannot be tested there without mocking everything that matters. A template puts the FR-011 question in front of the reviewer on every pull request at no cost.
- **Alternatives considered**: ShellCheck or Bats (new tools needing approval); an automated compatibility test running the previous release against the new schema (needs two builds and a database in CI; the spec chose review).
